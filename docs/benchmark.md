# Optimized checked language comparison

The measurement round compares the existing M1 codecs and M2 Blake2b-256 adapters on one host.
It complements the M3 resource/lifetime evidence from the persistent and integrated workloads.
It does not time the soak's deliberate waits or use them as networking throughput numbers.

Protocol definitions remain Gray Paper v0.7.1 at
`1c979cb59bb800f92ffff083a2701004dfc6cd33`: C.1.1 naturals, C.1.7 fixed integers,
C.1.2 byte strings/sequences, C.2 work digests and Cryptography's Blake2b-256. Compiler, vector and
backend pins are unchanged. Official tiny work-result binary/JSON pairs are independently checked;
the other fixtures are generated by the existing separate Python mathematical codec oracle.

## Run

```sh
python3 interoperability/benchmark.py --fetch
# After the existing crypto build has been verified, as in CI:
python3 interoperability/benchmark.py --reuse-native
# Reuse only binaries built from the current measured sources:
python3 interoperability/benchmark.py --skip-build
# Plumbing smoke test only, not decision evidence:
python3 interoperability/benchmark.py --reuse-native --quick
python3 interoperability/test_benchmark_harness.py
```

The Linux workflow runs the full comparison after correctness/integration tests. Every native child
is pinned with `taskset` to the same allowed Linux CPU. No other measurement child runs in parallel.
The local Mac run has no enforced CPU affinity and is exploratory evidence; do not substitute its
numbers for the Linux target. Shared CI hardware can still experience host load/frequency variation.

Output lives in `build/bench`: a human-readable table, complete JSON, corpus hashes, exact build
commands, compiler/hardware metadata, binary/source hashes and raw per-process logs. Each run has
its own raw-log directory. A new run clears the previous success marker before rebuilding; partial
JSON has `complete: false`. `--reuse-native` relies on the preceding verified native builder;
the exact linked crypto library hash and expected dependency pins are recorded. `--skip-build`
likewise requires current binaries and records their hashes, but has no new compiler command list.

## Cases and operation contracts

The 69 case/operation pairs cover:

- Naturals at zero, 127, 128, 16384, 2^56 and uint64 maximum; encode and decode.
- Fixed unsigned widths zero, four and eight; encode and decode.
- Byte strings with zero, 32, 1024, 65536 and 1048576 payload bytes.
- Four-byte scalar sequences with 32, 1024 and 16384 elements; encode and decode.
- Two official work digests, plus successful 1 KiB, 64 KiB and 1 MiB nested payloads with
  full-width gas/natural boundaries.
- Blake2b-256 on 32-byte, 1 KiB, 64 KiB and 1 MiB raw messages, checked against Python hashlib.
- A common call/observation control without codec work.

Byte strings and digests include borrowed decode, ordinary encode, owned decode and prepared owned
encode. All input/encode values and destination buffers are prepared before timing. Borrowed
input remains stable. Owned decode includes metadata selection and final ARC/manual release;
prepared owned encode retains one preflighted snapshot and excludes decode/allocation. No hidden
owned round trip is labelled as encoding. Sequence decode writes caller-owned preallocated values.

Blob-span decode checks framing/bounds and returns coordinates. It does not read/copy each payload
byte. Work-digest decode likewise validates fields/metrics while leaving its byte output borrowed.
Their near-constant time over large blobs is part of the API contract; reporting apparent payload
GiB/s for these operations would misrepresent what the decoder does.

## Optimization and integrity

Nim uses ARC, clang, `-d:release --opt:speed --passC:-O3` and explicit assertion, bounds, range,
field and overflow checks. Odin uses `-o:speed -vet -strict-style`, with assertions/union checks
retained. No LTO, native-code tuning or unchecked fast mode is introduced.

Each adapter uses a noinline operation wrapper, consuming runtime-loaded inputs and checking its
real result. A common separately compiled C observation function takes the complete result/output
address through a non-LTO opaque ABI boundary. Its implementation neither reads nor writes those
bytes. This prevents discarded result fields/output copies from disappearing under optimization.
The C library implements only observation and normalized process peak RSS, not any codec/crypto.

Before timing, the adapters check exact consumed lengths, verify complete encoder output bytes
and emit an operation fingerprint. Python independently checks each fingerprint, the loop checksum
and the actual Blake2b digest. The baseline exposes common wrapper/observation cost; no baseline
subtraction turns tiny differences into misleading negative times. Dynamic dispatch/check overhead
in the benchmark wrapper is included, so very small cases need cautious interpretation.

Eight regression tests reject wrong results/checksums/digests, missing samples, hidden allocations
and unreleased owners, and keep the two sampling methods distinct. Local malformed-natural probes
also confirm the optimized binaries reject failed decodes through their assertion guards.

## Timing and allocation observations

A three-batch calibration chooses the same iteration count for both candidates using the slower
candidate's observed duration. Default batches target about 10 ms and cap at twenty million calls.
Each case runs three fresh processes per language, fifteen throughput batches per process, and
128 single-operation latency samples per process. Candidate order alternates; case order uses a
fixed shuffle seed. Warmup occurs before recording. File parsing, preflight scans, printing, process
startup and Python IPC are excluded from native monotonic-clock intervals.

The JSON retains 45 batch averages and 384 actual operation samples per language/case, including
between-process medians. Batch median/p95/p99 describe **batch-average ns/op**, not operation tails.
Separately labelled single-operation median/p95/p99 include timer and observation overhead, which
can dominate sub-100 ns operations. These are warm-cache microbenchmarks, not concurrent service
latency or sustained bandwidth on a streaming corpus. One run does not establish statistical
significance, cold-cache behavior or scaling under load.

Allocation instrumentation uses separate optimized binaries: Nim's `nimAllocStats` public counter
and Odin's tracking allocator. The pinned Nim counter's fields are private; its supported standard
printable representation is parsed without runtime patches. Instrumented durations are never used
as speed measurements. Counts start after setup/warmup; allocations and releases must balance.
Borrowed/prepared operations must allocate zero; owned decode must exercise actual allocation.

Nim reports allocation/release calls and occupied-memory delta, but this counter provides no
requested-byte total. Odin additionally reports requested bytes. These are language allocator
observations, not OS malloc calls or C-backend attribution. Process peak RSS includes fixture,
output, snapshot and runtime storage; it is not a codec-only retained-memory measurement.

## Interpretation and next decision evidence

Use the generated tables to compare current implementations on the same host and corpus. M2
numbers include different existing providers (BoringSSL for Nim, compiler core for Odin). Their
ratio includes provider choices as well as adapter/compiler effects. Shared Bandersnatch Rust and
network stacks are covered by existing conformance/integration/resource evidence, not a new
speed ranking in this round.

[The local report](../results/benchmark.md) records measurements and a separate profiling check
of the large-copy gap. Profiling samples are never included in benchmark timings. Production
source remains unchanged; a measured implementation hotspot can warrant a separate bounded
optimization before drawing a language conclusion.

Linux CI results and the maintainer's reading/debugging preferences remain material to selection.
Existing IPv6, independent-peer, outgoing-engine and crypto-policy/audit limits also remain as
previously recorded. No automatic language winner or timing pass/fail threshold is applied.
